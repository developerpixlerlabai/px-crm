Outbound OS Teardown

The PRD is unusually good — the instincts are right and most of it should be built. The problem is that it describes a five-layer intelligence system on top of a codebase that is currently a read-only dashboard over a Google Sheet, and it budgets 10–15 weeks for roughly 20–24 weeks of work. Here is what I would build, in what order, what I would cut, and the one thing I would do before writing any of it.

01

The verdict

whole document

Six things matter more than everything else in this assessment. If you read nothing past this section, read these.

Keep — the PRD's core thesis is correct

Trigger-based outbound, company-as-primary-entity, mandatory dedup, an append-only event log, explainable scores, and revenue as the feedback signal. These six decisions are the difference between a real system and a scraper with a UI. They are all in the PRD, stated clearly, and none of them should be negotiated away for speed. Sections 2, 4, 8, 26, 31 and 40 are the spine of the product.

Change — the phase order delays value by three months

Section 49 builds each layer fully in turn: all of Foundation, then all of Intelligence, then all of Outreach. Under that order nothing is testable against a real prospect until week 8, because an intelligence layer produces no value until outreach and replies flow through it. Section 50's own MVP definition contradicts section 49 — and section 50 is right. Build one narrow vertical slice end to end first: one source, one campaign, rules-only scoring, approval-gated sending, reply capture. That is ~6 weeks and it teaches you more than 8 weeks of layer-building.

Add — the three things the PRD does not mention at all

1. A job runtime. Ninety percent of this system is background work — ingest, enrich, score, route, send, poll, classify. The PRD never says what executes it. Next.js route handlers on Vercel have execution limits and no retries; this needs a durable queue with steps and backoff before any pipeline code is written. It is a foundational choice, not an implementation detail.

2. Deliverability as a first-class subsystem. The PRD spends ~15 sections on scoring and AI and roughly two paragraphs on email infrastructure. Inverted priorities: cold outbound programs die of bounce rates, spam complaints and burned domains far more often than of insufficiently clever lead scoring. Bounce rate above 3% and a complaint rate above 0.1% will end the program regardless of how good the model is.

3. Legal basis for contact. Scraped addresses sent to EU, UK and Canadian recipients carry real exposure under GDPR, PECR and CASL — and Shopify storefront scraping yields exactly the role addresses (support@, info@) that generate complaints. This needs a decision, a suppression architecture and a retention policy, not a bullet under Security.

Cut — the learning engine, for now

Section 28 wants the system to detect that one segment outperforms another and propose weight changes. The arithmetic does not support it yet. At PixlerLab's likely deal volume, a "3.4x higher positive reply rate" measured on 40 prospects per arm is indistinguishable from noise. Instrument everything from day one so the data accrues — that part is cheap and mandatory — but ship the analysis as a human-read report with sample sizes and confidence intervals attached, and gate any recommendation on a minimum n. Automated weight proposals are a month-12 feature, not a phase-5 feature.

Blocker — the app has no authentication and a live mailbox attached

Your own docs/GMAIL-SYNC.md marks Phase 0 as deferred and gates deployment on it. That assessment is correct and it is now the highest-priority item in the build. There is a connected Gmail account whose refresh token the app can decrypt, and no login in front of any of it. On localhost that is fine. On a Vercel URL it publishes the team's mail to anyone who finds the hostname. Nothing else ships until this does.

The one thing to do first

Run a 100-lead manual pilot in parallel with Phase 0, before any pipeline code exists. Hand-pick 100 companies in one segment, write the emails by hand, send them from a warmed mailbox, and measure positive replies over two weeks. This costs one person a few days and it tests the only assumption the entire five-month build rests on: that PixlerLab's offer lands with a cold audience at all. If 100 hand-written emails to hand-picked prospects produce fewer than two positive replies, the problem is the offer or the list, and automation will reproduce that failure at scale with excellent dashboards. Full detail in section 16.

The four assets worth building on

Most of the existing code is narrow, but four pieces are genuinely good and should set the pattern for everything that follows rather than being rewritten.

  • The Vault + SECURITY DEFINER secret pattern in 0001_mailboxes.sql. Correct on all four counts that matter: plpgsql not sql, search_path = '' with fully-qualified identifiers, granted to service_role only, and explicitly revoked from public / anon / authenticated. Reuse this for the Apify and Instantly API keys instead of env vars, so third-party credentials become rotatable and auditable.
  • The unwrap() idiom in sheets.ts, which translates a provider's unhelpful response into an actionable message ("redeploy with Who has access: Anyone"). Every new integration client — Apify, Instantly, the enrichment provider — should have exactly this shape. It is the difference between a debuggable pipeline and a mysterious one.
  • The label-scope consent gate. A connected mailbox grants an entire account; gating reads behind an explicit label choice is a better privacy posture than most commercial CRMs manage. Keep it, and reuse the same gate for reply ingestion.
  • The component set. Twenty-one ui/ primitives on Base UI plus Tailwind 4, already themed. The new surfaces — approval queue, action queue, pipeline, analytics — should be assembled from these, per PRD rule 2.

One thing to retire deliberately

The Lead type in src/lib/types.ts is sheet-shaped: it carries row and key, and its 18 flat fields mirror spreadsheet columns A–R. It must not become the core domain type. Demote it to a source-adapter DTO — the thing the Google Sheet ingestion parses into, and nothing more — before any of the new model is written. If Lead leaks into the company graph, the graph inherits the spreadsheet's shape and section 30's warning ("avoid putting everything into one giant leads table") is lost on day one.

Where the PRD's estimate goes wrong

Three specific underestimates account for most of the gap, and none of them are padding.

  • Phase 1 at 1–2 weeks is the largest error. It contains the unified company model, the unified contact model, lead ingestion, deduplication, source tracking, CRM migration and basic scoring. Identity resolution alone (section 6) is a week—plus of careful work with tests, because getting it wrong silently corrupts every downstream number. Migrating the existing sheet without creating duplicates is another. Realistic: 4 weeks, and that assumes auth and the job runtime already exist.
  • Reply capture is not costed. The PRD folds it into Phase 3 as "reply ingestion". Doing it properly means a local mirror, Gmail push notifications via Pub/Sub, history cursors, duplicate-webhook handling and thread-to-company attribution. Your own Gmail doc correctly scopes that as its own Phase 2 and notes that most of the reference implementation's bulk exists purely to maintain that mirror. It is 3 weeks, not a bullet.
  • Nothing is budgeted for the work that has no feature attached. Auth and RBAC, the job runtime, the event log, the test harness, error tracking, staging, and the API-failure handling that rule 9 requires on every external call. That is 3–4 weeks in total and it is all real. It is invisible in a feature-shaped phase plan, which is exactly why feature-shaped phase plans run 2x over.
Read this the right way

20–24 weeks is not an argument against building it. It is an argument for sequencing so that value arrives at week 8 rather than week 20, and for being honest about the run-rate before starting rather than at week 12. A five-month build that is planned as five months succeeds; a three-month build that takes five months gets abandoned at month four with the intelligence layer half-finished and no emails ever sent.

Thirteen stages in four groups, with six cross-cutting concerns that the PRD's flow diagram leaves implicit. Each stage is a step in a durable job, reads from and writes to Postgres, and emits an event. Nothing calls the next stage directly — stages subscribe to events, which is what makes the loop in section 63 close without becoming a tangle of direct calls.

Cross-cutting

  • Event logAppend-only, one row per meaningful thing that happened. Every analytic in sections 25–27 is a query over it. Retrofitting this later is the single most expensive omission available.
  • Job runtimeDurable steps with retries and backoff. Every stage above is a step. Without it, rule 9's error handling has nowhere to live.
  • Identity & accessSupabase Auth plus real RLS policies. Phase 0. Everything else is gated on it.
  • SuppressionA single evaluator consulted by every send path. If there are two suppression checks, one of them is wrong.
  • ObservabilityPer-source run stats (section 56), plus error tracking with alerting. A silent ingestion failure is worse than a loud one.
  • SecretsVault-backed, following the pattern already in 0001_mailboxes.sql. Not env vars.

Data model, corrected

§7 · §30

Section 30's table list is close to right and its warning about one giant leads table is the correct instinct. Six changes matter, and each of them is cheap now and expensive later.

The six corrections

ChangeWhy it matters
Add source_records — immutable raw payloads Section 6 says preserve raw source data alongside normalised fields, but section 30 has nowhere to put it. Every ingest writes the untouched payload with an idempotency key and a fetch timestamp. This is what makes re-parsing possible when a normaliser turns out to be wrong — without re-scraping, and without losing the original.
Split company_domains out of companies A company has an apex domain, a .myshopify.com handle, a redirect origin and often a second brand. One domain column forces a false choice and guarantees duplicates. Many domains, one company, one flagged primary.
Split contact_emails out of contacts Section 7 puts email, email_status and email_confidence on the contact, which cannot hold a person with a role address and a personal address at different verification states. Verification and bounce history belong to the address, not the human.
Make signals typed and evidence-bearing A signal needs type, strength, evidence, source_url, observed_at and half_life_days. Section 9 lists the categories and section 7 has intent_expiry, but expiry is a cliff where decay is what actually happens: funding matters enormously at 10 days and barely at 120.
Persist every scoring run in scores Not a column on the company. A row per computation with the ruleset version, total, per-component breakdown and the human-readable explanation. Principle 5 is then satisfied by construction, and you can replay a new ruleset over last quarter's data to see what it would have done.
Separate messages from deliveries One composed message can be delivered through Instantly or Gmail, can be retried, and can bounce on one address and land on another. Collapsing content and delivery attempt into one row makes the section 27 funnel unqueryable within a month.

06

The five hard parts

§8 · §11 · §16 · §33 · §35

Everything else in this build is ordinary CRUD. These five will absorb most of the difficulty, and four of them get a single paragraph in the PRD. Each one below gets a concrete design, because "the system must merge these into one company" is a requirement, not a plan.

1. Identity resolution

Section 8 says dedup is mandatory and gives one example. It is the highest-risk data engineering in the project, because getting it wrong is silent: nobody notices duplicate companies until the revenue-by-source numbers stop adding up, by which time three months of outreach has double-touched prospects.

The real difficulties are not in the example:

  • Domain forms. www. prefixes, country subdomains, a Shopify store on brand.myshopify.com that also serves brand.com, marketing sites on a separate domain, parked domains that redirect somewhere else entirely.
  • Agencies with multiple brands and holding companies with a dozen operating names — where merging is sometimes right and sometimes destroys a real distinction.
  • Contacts without company domains — a founder using a Gmail address, which matches nothing and must not match everything.

The design

key   = registrable domain via the Public Suffix List   (tldts)
        lowercase, strip www., follow one redirect hop at ingest

auto  merge ONLY on exact registrable-domain match
queue everything else into merge_candidates for review
        candidates from pg_trgm similarity(normalised_name) > 0.45
        AND same country

undo  source_records immutable + companies.merged_into_id pointer
        unmerge = null the pointer, nothing is destroyed

Three rules make this survivable. Never auto-merge on a name match — "Apex Digital" is four different companies. Make every merge reversible, because you will get some wrong and an irreversible bad merge means restoring from a backup. Test it properly: this is a pure function over strings and it is the single best return on test effort in the codebase.

Idempotency is the other half. source_records.idempotency_key = hash(source, natural_id) with a unique constraint means re-running the same Apify actor creates nothing new — which is exactly what section 55 asks for, implemented as a database constraint rather than as care.

2. The score does not compose the way section 11 describes

Section 10 gives a table of additive point values (+35, +45, +40…) and section 11 defines the final score as Company Fit + Intent + Pain + Service Fit + Timing + Contactability, bounded 0–100. These two cannot both hold. A company hiring three engineers that raised recently with a large catalog is already at 120 from the section 10 table alone, before the other five dimensions are added. Clamping at 100 then destroys the ranking precisely among the best leads, which is the only place ranking matters.

The fix

-- each sub-score normalised into 0..1 by its own rules
s_fit, s_intent, s_pain, s_service, s_timing, s_reach  in [0,1]

-- weights are admin-editable and must sum to 1 (§10)
raw   = SUM( w_i * s_i )            -> 0..1
score = round(100 * raw)            -> 0..100, and it means something

-- time-sensitive signals decay rather than expiring on a cliff
strength(t) = strength_0 * 0.5 ^ (t / half_life)

    funding      half_life  60d      fresh capital gets stale fast
    hiring       half_life  30d      a filled role is not a signal
    catalog/tech half_life 365d      effectively structural

Keep v1 entirely deterministic and rule-based. It is explainable for free (principle 5), it is testable, and an admin can reason about a weight change. The moment to consider anything learned is when there are enough outcomes to fit against, which is section 8's problem and is a year away.

Where this should eventually go

A 0–100 score answers "how good is this lead" but the question a salesperson actually has is "what should I do first". Those differ whenever deal sizes differ. The right long-run ranking target is expected value — P(positive reply) × P(win | positive) × expected deal value — which correctly prefers a 65-scored enterprise Shopify store over an 80-scored small agency. Build the 0–100 score now, persist every component of it, and you will have the training data to make that switch when the outcomes exist. Do not attempt it in phase 2.

3. "Never invent facts" is a mechanism, not a prompt line

Section 35 lists seven things the AI must never do and section 16 adds seven rules it must follow. All fourteen are stated as instructions to the model. Instructions reduce hallucination; they do not prevent it. Since the entire value proposition here is messages grounded in real intelligence, a single invented funding round sent to a real CEO costs more than the system saves that month.

Three mechanisms that actually enforce it

  • The fact pack is the only input. The composer builds a whitelisted JSON object of verified fields, each carrying its source_record_id and observed_at. The model never sees a raw scrape, a page dump or an unverified enrichment. If a fact is not in the pack, the model has no way to know it — which converts "do not invent" from a request into a property of the input.
  • A validator runs after generation. Extract every numeral, proper noun and technology name from the draft; each must appear in the fact pack or on a small stoplist of generic terms. A miss means one regeneration, then the draft routes to a human with the offending span highlighted. This is perhaps 150 lines and it is the difference between a guardrail and a hope.
  • Every generation is recorded. ai_runs stores the prompt version, model, fact pack, output, validator verdict and token cost. When a prospect replies "we never raised a Series A", you can see exactly what the system believed and where it came from.

Two of section 35's items are not model behaviour at all and should not be left to the model: ignore unsubscribe requests and send high-risk messages without approval are enforced by the suppression evaluator and the approval mode on the campaign. A prompt cannot fail to send an email.

4. The Instantly boundary — where principle 3 will actually break

Principle 3 says one lead, one source of truth, and names Instantly as a system that must not become a second database. But Instantly is a database: it holds its own lists, its own sequence state, its own unsubscribe list and its own reply detection. If both systems can decide who gets contacted, they will disagree within weeks, and the failure mode is double-touching a prospect who already replied — the most expensive mistake in outbound.

ConcernOwnerNotes
Audience selectionCRMRouting decides membership. Nobody edits an Instantly list by hand, ever.
SuppressionCRMOne evaluator, consulted at enrolment and again immediately before push. Instantly's own list is a backstop, not the authority.
Sequence stateCRMWhich step, when the next one is due, and every stop condition in section 19.
Message contentCRMComposed and approved locally, pushed as a rendered body. No templating in Instantly.
Sending & deliverabilityInstantlyMailbox rotation, warm-up, throttling, domain health. This is what you are paying for.
Delivery eventsInstantly → CRMWebhooks for sent, delivered, bounced, replied, unsubscribed. Each writes an event; a reducer updates state.

Expect duplicate webhooks and out-of-order delivery, and make the reducer idempotent from the start — section 55 asks for exactly this and it is much easier to build in than to add.

The alternative worth considering: you already have working multi-mailbox Gmail OAuth with send. For volumes under roughly 500 emails a week, sending through your own warmed mailboxes and dropping Instantly entirely removes this whole class of problem and one vendor. The trade is that you then own warm-up, rotation and domain reputation yourself — which is a real job. My recommendation is to keep Instantly for cold volume on dedicated domains and use the Gmail path for one-to-one high-value outreach and all replies. But it is a genuine decision and it should be made deliberately in phase 3, not by default.

5. Inverting the Google Sheet

Today the sheet is the source of truth: Apps Script appends to it daily and the dashboard reads and writes six columns. Section 33 wants the CRM to become primary "long-term", which is the right destination and a vague plan. Cutting over badly means either losing edits or running two divergent copies of the lead list. 

step 1  Apps Script keeps appending AND posts to /api/ingest/google-intent
        one-time backfill of existing rows through the same idempotent path
        CRM is populated; sheet is still authoritative      ~1 week

step 2  dashboard reads from the CRM; writes go to the CRM
        CRM writes a nightly read-only mirror back to the sheet
        anyone still living in the spreadsheet sees current data  ~2 weeks

step 3  Apps Script stops appending, becomes a pure producer
        sheet is a nightly export and nothing more
        CRM is canonical                                    cutover

The mirror in step 2 is what makes this safe: it costs half a day and it removes every argument about cutting over, because nobody loses the view they are used to. Keep it running for a month after the cut, then delete it.

On the two email numbers that are missing from §57

Where I disagree

Five judgements in the PRD I would change, with what I would do instead. Everything not listed here I agree with, which is most of the document.

PRD positionVerdictWhat I would do instead
§49 — build each layer fully before the next change Cut a thin vertical slice through all layers first. Section 50's own MVP definition already describes this; section 49 contradicts it. §34 — seven AI agents in the pipeline change The decomposition is right, the coverage is not. Running seven model calls over every discovered company costs roughly $1,125 a month against about $12 for the gated version (worked through in section 11) — a ninety-fold difference for no additional revenue. Deterministic rules run on 100% of leads; models run only on the slice you will actually contact. What I strongly agree with

Worth stating explicitly, because these are the parts that most PRDs get wrong and this one does not:

  • Principle 1, intent over volume. The failure mode of every outbound system is optimising for list size. Naming this as principle one is the single best decision in the document.
  • Principle 5, explainability, and the requirement in §12 to label pain as a hypothesis. A system that says "possible performance issue, based on a 25,000-product catalog on a customised Prestige theme" is honest and useful. One that says "your site is slow" without having measured it is a liability — and section 35 correctly forbids it.
  • §36 defaulting new campaigns to Review mode. Correct, and it should be enforced by the schema rather than by convention.
  • §29 lead-quality feedback from salespeople. Cheap to build, and the most valuable training data the system will ever have. Build it in phase 2 even though nothing consumes it until much later.
  • §53 rule 1, do not rewrite the existing application. Correct, and the Gmail and Vault work is worth keeping.
  • §43 opportunity memory. Cheap — a structured note plus a reactivation date on the company — and "their agency contract ended" is genuinely the highest-conversion moment in outbound. Build the simple version early.

The MVP cut line

§50 · §51

Section 50 is right that the whole vision should not be attempted at once, and its loop is the correct loop. But the version below is narrower still: one source, one campaign, one segment. The goal is not a usable CRM at week 8. It is evidence, at week 8, about whether the loop closes at all.

Sources1The AI-hiring detector you already have. Not Shopify, not funding, not healthcare.
Campaigns1One ICP, one offer, one five-step sequence.
Model calls per lead1Personalisation only. Scoring and routing stay deterministic.
Approval modereviewEvery message read by a human before it sends. No exceptions in the MVP.

In

  • Auth, the job runtime and the event log — all of phase 0, none of it optional.
  • Ingestion from the one source, with idempotency and domain-based dedup.
  • Companies, domains, contacts, emails, typed signals.
  • A deterministic six-component score with a visible breakdown.
  • One campaign, one sequence, the suppression evaluator, client protection.
  • Fact-pack composition with the validator, and an approval queue.
  • Sending through one path (whichever you choose in section 15) with a hard daily cap.
  • Reply capture and classification, with a task landing on someone's queue.
  • Four numbers on a screen: contacted, replied, positive, meetings.

Out

  • Every other lead source, including the Shopify and Apify pipeline.
  • Multi-campaign routing, secondary campaigns, campaign analytics.
  • Deals, revenue, attribution, the management dashboard.
  • Merge review UI — log candidates to a table, look at them in SQL.
  • Admin-editable weights — a constant in a file is fine at this stage.
  • Enrichment providers — use whatever contact data the source already yields.
What week 8 tells you

By the end of the MVP you will know three things you cannot know today, and each of them changes what gets built next. Does the offer land? — measured in positive replies, not opens. Does the score correlate with anything? — compare reply rates above and below the threshold; if they are the same, the scoring model is decoration and phase 2 needs rethinking, which is enormously valuable to learn at week 8 rather than week 20. Does anyone work the queue? — if tasks pile up unworked, the constraint is staffing, and no further engineering fixes it.

Roughly a ninety-fold difference for no additional revenue, since the six thousand companies you were never going to contact do not care how carefully they were analysed. At the midpoint, roughly $900 a month, the system needs to produce about one additional $10,000 project per year to cover its running costs, and roughly three to five per year to cover the build at a realistic blended engineering rate. Against a 20-person delivery team's revenue that is a low bar — which is the real argument for building this. It is worth stating in the PRD, because section 57 asks for ROI without ever establishing the denominator.

Build vs buy

strategic

The PRD assumes building. That is defensible here, but not for every layer, and the assumption deserves to be stated rather than inherited.

LayerVerdictReasoning
Email verificationbuySolved, cheap, and getting it wrong burns domains. No upside to building.
Sending infrastructurebuyWarm-up, rotation and deliverability are a specialist ongoing job, not a feature.
Contact enrichmentbuyYou cannot out-collect Apollo. Buy the data, own what you infer from it.
Calendar & meeting bookingbuyCal.com or Calendly with a webhook into the event log. A week saved for no loss.
The company graphbuildThis is the asset. It compounds, it is yours, and it is what makes year two better than year one.
Signals, scoring, routingbuildEncodes PixlerLab's specific judgement about who is worth contacting. Nothing off the shelf knows that a customised Prestige theme on a 25,000-product catalog is a Shopify performance lead.
Fact-grounded compositionbuildThe validator and the provenance chain are the differentiator. Generic AI writers have neither.
The attribution loopbuildThe reason the system exists. Section 63 is right that this is the architectural principle.

The alternative worth naming

Clay plus a standard CRM plus Instantly would reach a working version of the enrich-score-route-send loop in roughly two to three weeks rather than twenty. That is a real option and it should be rejected deliberately rather than ignored. The trade-offs are: per-credit costs that grow with volume rather than amortising; the company graph living in someone else's schema, so the compounding asset is rented; and the attribution loop — the actual point of the product — being the part Clay does least well.

Building is nonetheless the right call here, for three reasons the PRD does not state. You already own the hard, differentiated half: the Apify Shopify intelligence and the Google intent detectors are the parts that are genuinely difficult to buy. This is PixlerLab's own competence — a 20-person development team building an internal system is not a stretch assignment. And a working revenue OS is a credible sellable product and an unusually strong case study for exactly the services being sold. That last point is worth making explicit in the PRD, because it changes the calculus on tenancy: if this might one day be multi-tenant, the cost of leaving a space_id-shaped hole in the schema now is close to zero, and the cost of retrofitting one in year two is very high.

Decisions I need

blocking

Eight decisions that change what gets built. The first four block phase 1; the rest can wait until the phase that needs them. Where I have a recommendation, it is stated.

  1. 01
    Which single segment does the MVP target?
    My recommendation: AI hiring for the technical pilot, white-label agencies for the manual pilot. AI hiring has the cleanest signal and you have already built the detector, so the pipeline can be proven without also solving discovery. White-label agencies have the best economics — repeat buyers, recurring work, a buyer who needs no education — but the list is harder to build, so start it by hand. Running both answers two questions at once.
  2. 02
    Inngest, or a self-hosted queue on Postgres?
    My recommendation: Inngest. Durable steps, retries and fan-out for free, and the thirteen stages map onto it directly. A jobs table with pg_cron avoids a vendor but means writing retry, backoff and dead-letter semantics yourself — roughly a week you could spend on the graph instead. Choose before phase 0, because everything else sits on it.
  3. 03
    Are EU and UK prospects in scope?
    This is a business decision with engineering consequences and it cannot be deferred past phase 1, because it determines whether territory becomes a suppression dimension and whether an erasure path is required. If the answer is yes, budget for counsel and a documented legitimate-interest assessment. If US-only is acceptable commercially, the compliance surface shrinks dramatically.
  4. 04
    Who operates this daily, by name?
    Not a role — a person. Sections 24, 29 and 36 all assume someone clears tasks, approves drafts and marks lead quality every working day. If that person does not exist, halve the scope and build toward a system that surfaces ten leads a week to a founder rather than one that manages a queue nobody works. This changes the design more than any technical decision on this list.
  5. 05
    Instantly, your own Gmail mailboxes, or both?
    My recommendation: both, split by purpose. Instantly for cold volume on dedicated domains; the Gmail integration you have already built for one-to-one high-value outreach and all reply handling. Under about 500 sends a week, dropping Instantly entirely is viable and removes a whole class of state-synchronisation problems — at the cost of owning warm-up and domain reputation yourself. Decide in phase 3.
  6. 06
    What is the monthly ceiling on enrichment spend?
    Per-record costs scale with list size and this is the largest recurring line. A hard cap enforced in code, with the pipeline degrading gracefully rather than failing when it is hit, is much better than a surprise invoice. Needed before phase 1's enrichment work.
  7. 07
    One engineer or two?
    Two devs take this to roughly 13–15 weeks rather than 20–24, splitting cleanly at the ingestion / outreach seam after phase 1. It does not halve, because the graph work in phase 1 is inherently serial and everything depends on it. If it is two, the second person's best first task is the Instantly and Gmail delivery layer, which is genuinely independent.
  8. 08
    Internal tool only, or a future product?
    If there is any chance this is sold or offered to clients, leave a space_id-shaped hole in the schema now. Your Gmail doc already notes that adding tenancy later is "a mechanical change to the RLS predicates" — that is true while the schema is small and stops being true once thirty tables and an event log exist. Costs almost nothing in phase 1.
16

Start here

week 0

Two things happen before any pipeline code is written. One is engineering and takes two weeks. The other is not engineering at all, takes a few days of one person's time, and is the highest-value action available in this entire document.

Track A — Phase 0, immediately

Auth, the job runtime, the event log, the test harness, error tracking. Two weeks, no features, and it unblocks deployment of everything that already exists. Your own Gmail documentation already identifies this correctly and it has been deferred once; deferring it again means the Gmail work that is finished cannot ship.

Track B — the 100-lead manual pilot, in parallel

Hand-pick 100 companies in the chosen segment. Write the emails by hand — personalised from real observations, exactly the way the system is eventually meant to. Send them from one warmed mailbox over two weeks. Reply to everyone who answers. Count positive replies and meetings.

Cost~3 dOne person, plus a warmed mailbox you already have.
Teststhe offerThe one assumption the entire build rests on and never checks.
Green light3–8Positive replies. Build the full scope with confidence.
Red light0–1Fix the offer or the segment first. The system would only scale the miss.

The pilot also produces things the build needs and cannot invent: the messages that actually earned replies become the few-shot examples for the composer; the objections you hear become the reply classifier's categories; and the reasons you personally rejected companies while hand-picking the list are the scoring rules, written down for the first time. Section 16 of the PRD asks the AI to explain why a company was selected. Track B is how you learn what that explanation should say.

The honest summary

This is a good PRD describing a system worth building, and the codebase underneath it is smaller and cleaner than the document assumes — which is mostly good news, because there is little to unwind and the Gmail and Vault foundations are solid. The two real risks are not technical. One is that twenty weeks of work is planned as ten and gets abandoned at week twelve with the loop still open. The other is that the loop closes perfectly and nobody works the queue.

Plan for twenty. Name the operator. Prove the offer by hand first. Then build it in the order above, and the closed loop that section 63 calls the most important architectural principle in the product will actually close.
